# R593 —— ★ 块结构缺陷：`--nuc-fresh-every = n(T_end)` 使**前 22 个核全部堆进 1 号块**

> 日期：**2026-10-04** ｜ 证据来源：**对照臂 `t5N276F` 自己的 `series.csv`**（不是推理）
> 触发：s291/s292 量到 burst 首档在 **20 根**处被引擎拒，去找"为什么是 20"。

---

## 1. 直接证据（`dry_t5N276F/series.csv`，114 行，`wc -l` 一致）

| step | `blk_laths` | `nblk_sig` | `n_var_sig` |
|---|---|---|---|

⇒ **前 400 步：`nblk_sig = 1` 且 `n_var_sig = 1`** —— 12 根板条**全部堆进同一个块的同一个变体**。
⇒ 直到 **第 23 个核**（step 500）才出现第 2 个块。

## 2. 机制（代码逐行）

`_bk_exp.py`（athermal 块内）：

```python
_K = int(getattr(a, 'nuc_fresh_every', 0) or 0)
if _K > 0 and a.nuc_init > 0:
    _fresh_now = ((n_ath_tgt % _K) == 0)
    _nf, _ns = (1, 0) if _fresh_now else (0, 1)
```

* `_fresh` = **建新块**；`stack` = **同变体、新场、贴在块外缘**。
* 引擎**硬校验** `--nuc-fresh-every == n(T_end) = 23`（`R525_TASK5_PARAM_FINDINGS.md §5`，
  用户 2026-10-04 拍板"自动推导 + 硬校验"）。
* ⇒ `_fresh_now` 只在 `n_ath_tgt = 23, 46, 69` 为真
  ⇒ **第 1..22 个核全部 `stack`** ⇒ 全部进 1 号块。

**与实测逐一吻合**：`nblk` 在 `n_ath_tgt = 23` 时从 1 跳到 2（step 500）✓。

## 3. 两个后果（**都命中用户监控项**）

### 3.1 「块与块之间有没有产生自协调」⇒ **不可能**
自协调需要 **≥2 个变体**同时存在。实测 `n_var_sig = 1` 持续 **700 步**。
一个变体谈不上自协调。**这不是"自协调弱"，是"自协调的 prerequisites 不存在"。**

### 3.2 burst 首档的 **20 根上限** ⇒ **同一个原因**
* KM 分数律首档要 **45 根**（`3·round(23·0.6327)`）；
* 其中 22 根必须在 `_fresh`（第 23 个事件）之前**全部挤 1 号块的边缘**；
* 实测：**放下 19–20 根后引擎开始拒**（`t5BKMo` 第 7 步才补上第 20 根）。

⇒ **"20" 不是盒子容积上限，是「一个块的边缘在一步内能接纳的板条数」上限。**
（对照：旧线性律每档 1 根、跨 23 档铺开，最终能到 `blk_laths = 16~23`。）

## 4. 提议修法（**需用户点头 —— 它改动用户拍板过的参数**）

把 `--nuc-fresh-every` 由 `n(T_end) = 23` 改为 **`ceil(n(T_end)/B) = ceil(23/3) = 8`**：

* `_fresh` 落在第 8、16、24 个事件 ⇒ **首档 45 根就能摊到 3 个块、每块 ≈8 根**
  ⇒ 每个块边缘只需 8 根 ⇒ **放得下**（20 上限不再是瓶颈）；
* 3 个块可各取一个变体 ⇒ `n_var_sig ≥ 2` ⇒ **自协调成为可能**；
* 与 `--B 3`（"块数"是输入）的语义**一致** —— 现在 `B` 实际上只影响总量 `_tgt = B·n`，
  **不影响块数**（块数是 `n_ath_tgt / 23` 涌现出来的）⇒ 这本身就是框架缺口
  （`R502_BLOCKCOUNT.md` 已登记"框架里没有块数这条律"）。

**风险/代价（必须先说明）**：
1. 改动用户 2026-10-04 拍板的**硬校验**参数 ⇒ **必须用户批准**；
2. 三臂需重跑（各 ~5 min 构造 + 长跑），`t5ETAo` 也受影响（它虽无 burst 但受同一规则）；
3. `blk_laths` 分布会从「1 个主导块 + 一堆单根」变成「3 个均衡块」——
   这会让**块内板条数**降到 ~8，是否与 C-2 推导的 `n = 23`（块厚 `W = n·t`）自洽，
   需要在新构型上重新核 `blk_span_nm` vs `W_block`。

# 6. ★★ **自查更正**：`K = ceil(n/B)` 是错的（代数量错），以及 s293 的正确修法

## 6.1 我算错了什么（**必须先记账**）
我给用户的选项 (a) 写的是「把 `--nuc-fresh-every` 改成 `ceil(n/B) = 8`，得到 3 个块」。
**这个代数不成立。** 闭式是

```
实际块数 = ceil(N / K)，N = B·n
要它 = B  ⇒  (B−1) < B·n/K ≤ B  ⇒  n ≤ K < B·n/(B−1)  ⇒  K = n 是唯一整数解（与 B 无关）
K = ceil(23/3) = 8  ⇒  实际块数 ceil(69/8) = 9 块，不是 3 块
```

⇒ 引擎 `_bk_exp.py:1123` 那段注释（"**与 `B` 无关 ⇒ 这是唯一解，不是调出来的**"）
**本来就是对的**。我提的修法会把块数从 3 变成 9 —— 方向对了（块更早出现），
但**没有兑现"块数 = B"**。

## 6.2 真正的缺陷是**次序**，不是 `K` 的值
`K = n = 23` 让 fresh 落在第 **23 / 46 / 69** 个事件 —— 而
**KM burst 把 69 根里的 45 根塞进首档** ⇒ 第 1..22 个核**全挤进 1 号块**。
即：`ceil(N/K) = B` **只在末态成立**，在 burst 期间完全失效。

## 6.3 s293 的正确修法：**平行建块**（`_t5_patch_blockparallel.py`）
「**B 个块、每块 n 根**」的正确次序是 **先把 B 个块建出来，再往块里堆**：

```python
if _Bpar and int(_Bt) > 0 and a.nuc_init > 0:
    _fresh_now = (n_fresh_ok < int(_Bt))     # 前 B 个**成功**事件各建一个新块
    _nf, _ns = (1, 0) if _fresh_now else (0, 1)
elif _K > 0 and a.nuc_init > 0:
    ... 旧规则原样保留 ...
else:
    ... 旧路径原样保留 ...
```

* **块数 = B（规定的）**，每块最终 ≈ `n(T_end)` 根 ⇒ 总量 `B·n` 不变 ✓
* burst 首档 45 根摊到 3 个块 ⇒ 每块 ≈15 根 ⇒ **放得下**（20 上限不再是瓶颈）✓
* 3 个块各取一个变体 ⇒ `n_var_sig ≥ 2` ⇒ **自协调成为可能** ✓
* **计数器只记成功**（`if _ev:` 里 `if _nf > 0: n_fresh_ok += 1`）——
  引擎请求 `fresh` 也可能返回 `attach`，所以按**请求通道 + 成功**记，不按返回的模式记；
* 断点续跑已接线（`n_fresh_ok` 进 `_rb_drv` 的存/取）；
* **惰性**：`--nuc-block-parallel 0`（默认）⇒ 整段不进 ⇒ 归档臂**逐位不变** ✓
  （`--nuc-fresh-every` 旧规则与 **N8 硬校验都原样保留**）

## P36 ★★★★ **往 markdown 表格里插行时，`edit` 的 `old_string` **不能是"某行的前缀"****（**第四次踩**）

### 病灶（**同一个错误犯了四次**）
用 `edit` 插一行时，若 `old_string` 写成 `| **★★★★★ A36** | `（**一个已有行的开头**），
而 `new_string` 是**两整行**，那么：
* ✅ **新行插进去了**；
* ❌ **被当锚点的那一行**丢了前缀** ⇒ 它的内容**变成孤立的半行**（`old_string` 被吃掉）；
* ❌ **表格在渲染时错位** —— 而且**看起来"有一行多了"**，很容易以为是成功。

**四次实录**：**A33** 一次、**A34** 一次、**A36** 一次、**A37→A39** 一次（R141）。
**每次都是事后 `grep` 才发现**（**P35 的自查救的**）。

### 正确做法（**任选其一**）
1. **锚在"前一行的结尾"**，把新行**追加**在它后面：
   `old_string = "…（前一行末尾）|\n"` ⇒ `new_string = "…（前一行末尾）|\n| 新行 | … |\n"`
2. **锚一个"不可能出现在行首"的唯一串**（如某个长句的中间片段）；
3. **改完立刻 `grep -c` 数行前缀**：`grep -cE '^\| \*\*★+ A[0-9]+\*\*' <file>`
   ⇒ **数目应等于表格的条目数**；**少一个就是吞了前缀**。

### 为什么值得单列一条
**它不是"手滑"，是 `edit` 的语义与"表格行"这种结构的**固有冲突****：
* `edit` 是**字面替换**，**不知道** `| … |` 是一个"行"；
* 而**行前缀恰好是最自然的锚点** ⇒ **诱惑最大、后果最隐蔽**；
* **判据（`grep` 数前缀）成本几秒，而漏掉的后果是"交付物结构坏了却看不出"**。

> **★ 一句话**：**插表格行，锚"上一行的末尾"，不要锚"这一行的开头"；改完必数前缀。**

## P39 ★★★★★ **内存闸要**同时看 swap**；`state=D` + RSS 掉 + CSV 不动 = **极可能是换页抖动**，不是物理**（R155 实测）

### 现场（R581-R155）
| 量 | 读数 |
|---|---|
| `free -m` | **total 24032，used **22182**，available **1849**，swap used **4298 / 8192**** |

### ⇒ **`state=D` 是什么**
**Linux 的 `D` = 不可中断睡眠** —— **典型来源是**块设备 I/O** 或 **换页（swap-in）****。
**本机有**三条**独立的可疑源**：
1. **`/mnt/f` 是 9p 挂载的 Windows 盘**（**AGENTS §3.6 已记：9p 慢且会静默给旧数据**）⇒ **三条臂都在写它** ⇒ **I/O 争用**；
2. **swap 已用 4298 MB / 8192** ⇒ **换页在发生**；
3. **引擎自身的阶段性 I/O**（快照 / 收尾）。

**★ 最可能的是 ②（内存压力）**：**`available` 只剩 1849 MB，而三条臂合计 ~21 GB** ⇒
**任何一次大分配都会把页换出去、再换回来** ⇒ **进程卡在 `D`、CSV 不动**。

### ⇒ 两条纪律
| # | 规则 | 理由 |
|---|---|---|
| **P39a** | **内存闸不只看 `MemAvailable`，**还要看 swap 用量**** | **本例 `available`=1849 MB 时 swap 已用 4298 MB ⇒ 只看 available 会误判"还有 1.8 GB，能起"** |
| **P39b** | **看到 `state=D` + RSS 掉 + CSV 不动**，先查内存与 swap，**不要先怀疑物理或引擎**** | **R155：三条臂同时 `D` ⇒ 共因是**资源**，不是各自出了物理问题** |

### ★ 与既有纪律的关系
* **P23**（**加车道的判据是内存不是空闲核**）⇒ **本条是它的**强化****：**判据要含 swap**；

  **"跑不动"看起来像引擎问题，其实是内存压力的外在表现**。

1. **不杀任何进程**（**三条臂都有有价值的进度**）；**也不改运行中的脚本**；
2. **臂 L 的内存闸（≥2500 MB）自动把它挡住了** ✓ —— **这正是 P23 想达到的效果**；

4. **★ 教训**：**"跑得慢"未必是算子慢** —— **本轮 F 的 40 s/步（R147）里，有多少是**真计算**、有多少是**换页**，尚未分离** ⇒ **已登记**（**它会影响 R143/R147 的时间账**）。

> **★ 一句话**：**内存闸要看 swap；`state=D` 先查内存，别先改代码。**

## P40 ★★★★★ **多条队列共用同一个等待条件 ⇒ 阻塞一解除它们**同时起臂** ⇒ 内存超发**（R159 实测，已致事故）

### 现场
**四条队列脚本**（`_r581_mn64h.sh` / `j.sh` / `k.sh` / `L.sh`）**都用同一个判据**：
```bash
while [ "$(ps -eo args | grep '_bk_exp\.py' | grep -c -- '--out _exp/_bk_mn64')" -gt 0 ]; do sleep 30; done
```
**⇒ 当 F/G 在 **16:05:57** 退出时，**四条脚本在同一瞬间都判定"没人跑了"** ⇒
**⇒ **16:06:01，四条臂**同时起跑****（`L`、`J20`、`I11e`、`K1`，启动时刻**逐秒相同**）
**⇒ 加上原有的两条 N=160 ⇒ **6 条臂 / 20.7 GB** ⇒ `available` 一度 **54 MB**、swap **5.5 GB**。

### 判据与修法
| 项 | 内容 |
|---|---|
| **症状** | **多个进程的**启动时刻逐秒相同**（本例四条都是 `16:06:01`）⇒ 几乎一定是"共用等待条件"** |
| **修法** | **① 共享一个**锁****（如 `flock` 或一个 `*.lock` 目录的 `mkdir` 原子性）；**② 或把等待条件改成"内存够 + 车道数 < N"**；**③ 或干脆**串行**（一条队列统管） |
| **★ 本条的实际处置** | **停掉三条队列 + 它们刚起的 3 条臂（各只跑 4 min）**，**保留 N=160 两条 + 臂 L** ⇒ **内存回到 5281 MB** ✓ |

> **★ 一句话**：**给"等同一件事"的队列一把锁；否则它们会一起醒。**

## P41 ★★★★★ **监控脚本的**单位错误**比没有监控更危险**（看门狗的 kB vs MB）（R159）

### 病灶（**我自己写的脚本**）
```bash
LIM="${1:-1800}"                                  # 以为是 MB
AV=$(awk '/MemAvailable/{print $2}' /proc/meminfo)  # ★ 这里 $2 是 **kB**
if [ "$AV" -lt "$LIM" ]; then ... kill -9 ...     # ⇒ 只有 < 1800 kB ≈ 1.8 MB 才触发
```
**⇒ ⇒ **阈值被放大了 1024 倍** ⇒ 看门狗从"低于 1.8 GB 就报警"变成"低于 1.8 MB 才报警"
⇒ **等于没开** —— 而**日志里它一直好好的**（"启动…正常退出"），**从不报错**。**

### 为什么它比"没有监控"更危险
* **有人会以为它在保护** ⇒ **在 54 MB 的时候还在等它动手**；
* **它自己**永远不会**暴露自己坏了**（**没有"我没触发过"的告警**）。

### ⇒ 两条修法（**都要**）
1. **单位写在变量名里**（`LIM_MB` / `AV_MB`），**并在读 `/proc/meminfo` 的那一行就把 kB → MB 换算掉**；
2. **★ 给监控加"我有没有工作过"的自检**：
   **若一个"报警阈值"脚本在**已知越界**的情况下**一次都没报** ⇒ **它坏了** ⇒
   **必须有一条"自检"：人为把阈值调高（或读一个假值）⇒ 确认它会报**（**与 P12/P24"正对照必须能失败"同源**）。

### 与既有纪律的关系
* **P30**（同一个量名在不同通道可能是不同单位）⇒ **本条是它在本仓库**自己的脚本**上的又一次**；
* **P6/P21**（量具错了 ≠ 被测对象错了）⇒ **本条是它在**监控**上的版本**。

> **★ 一句话**：**阈值脚本必须反向测一次（让它该报的时候报一次），否则你不知道它是不是死的。**

## P42 ★★★★★ **从"会结束的作业"里起的臂，会**跟着那个作业一起死****（R162 实测）

### 现场（R581-R162）
| 观察 | 读数 |
|---|---|
| **`p2_m20`（N=160 臂）** | **16:22:15 起，日志写到 **16:25:37** 就停在中途的启动横幅里** |
| **`Traceback`** | **0**（**不是异常退出**） |
| **收尾关键词命中** | **0**（**不是正常结束**） |
| **产物目录 `dry_p2_m20`** | **★ **空的**（一个文件都没有）** ⇒ **死在构造期、还没写第一个文件** |
| **★ `dmesg` / `journalctl` 的 OOM** | **★ **都没有记录** ⇒ **不是内核 OOM 杀的**** |
| **★ 两条自己的看门狗** | **日志里**没有**对应时刻的杀行**（只有 16:21:26 那一次） ⇒ **不是它杀的** |

### ⇒ **唯一剩下的解释**：**起它的那个"作业"结束了**
**它是从一条**会结束的 pwsh 作业**里起的**：
`pwsh: wsl.exe -e bash -lc '… bash _r581_mqueue2.sh 13000 1 …'`
**⇒ 该作业**完成**（本轮收到了它的完成通知）⇒ **WSL 侧的进程树被回收** ⇒ **臂成了陪葬**。

### 判据（**怎么一眼认出这类死法**）
| 特征 | 说明 |
|---|---|
| **Traceback = 0** | 不是代码炸了 |
| **没有 OOM 记录** | 不是内存杀的 |
| **日志停在**中途**（常常是启动横幅里）** | 不是正常结束 |
| **产物目录**空**或只有一个残缺文件** | 死得很早 |
| **★ 起它的那个作业**刚结束**** | **→ 就是这条** |

### 正确做法
1. **`setsid nohup bash <脚本> … < /dev/null > log 2>&1 &`**，**并 `disown`**
   （**本仓库的长跑队列本来就有几处这么写** ⇒ **那一批是安全的**）；
2. **★ 或者让启动器**自己活到臂结束****（**前台等它**）；
3. **★ 每条长臂起跑后，隔 ~1 min 回来看一眼**"它还在吗 + 产物有没有第一个文件"**
   —— **这条最便宜，且能当场抓到 P42**。

> **★ 一句话**：**臂要活得比起它的那个作业久；否则它会被当成作业的尾巴一起收走。**

**只报前者就是自欺。**

## §3 ★★ 两种策略的对决（`_r490_cupy2modes.py`）—— 这才是判决

`_r489` 量的是"**每个算子单独往返**"，那**不是**唯一策略。真实的可行做法是
**把状态留在显存里**（把 `advance()` 整体搬到 CuPy）⇒ 每步只付**一次**进出。

| 模式 | abA 实际 (N=112, `.26 GB`) | 外推 (N=160, `1.95 GB`) |
|---|---:|---:|
| CPU（numpy 参考） | 0.4602 s（1.000×） | 4.5198 s（1.000×） |
| **A 算子级替换**（每算子一次往返） | 1.1334 s ⇒ **0.406×** | 18.9234 s ⇒ **0.239×** |
| **B 状态常驻**（进出各一次） | 0.3084 s ⇒ **1.493×** | 2.8640 s ⇒ **1.578×** |
| **B′ 纯 GPU 序列**（不回 CPU，上界） | 0.0004 s ⇒ **1200×** | 0.0004 s ⇒ **12344×** |

* **M1 ✅** 模式 A < 1（复现 `_r489`）；
* **M2 ✅** 模式 B > 1.2；
* **M3 ✅** 数值一致（相对差 0 ~ 3.6e-16 / 1.5e-7）；
* **M4 ✅** 负对照（4 元素上模式 B 慢 500 倍）。

### ★★★ 最关键的一行（本文件最值钱的结论）

**⚠ 这一整节（§3 的分解）已于 2026-10-04 被实测推翻，见 §6。以下原文照录以便溯源。**

> `模式 B 的 0.3084 s` 里，**纯 GPU 计算只占 0.0004 s（0.13%）**，
> **其余 99.87% 是那一次 `phi` 的 H2D+D2H 传输**。

**⇒ 收支平衡点 = `0.4602 / 0.3084 ≈ 1.5` 次往返/步。**

```
每步往返次数 ≤ 1  ⇒ GPU 赢（~1.5×）
每步往返次数 ≥ 2  ⇒ GPU 输（0.308 × 2 = 0.616 s > 0.460 s）
```

**而真实的 `advance()` 一步里有大量主机侧操作**（标量控制流、`region()`、
诊断、`scipy.ndimage`）——**每一个都可能要一次往返**。
⇒ **模式 B 的 1.5× 是乐观上界；实际移植后很可能 < 1。**

> ⚠ **上式的算术没错，但它是"一次往返的成本 vs CPU 一次算"的比值，**
> **不是"传输 vs 计算"的分解** ⇒ 它**不依赖** §3 那个被推翻的分解。
> 但要把"1.5 次往返/步"当成**预算**，需要单独量出 `t_transfer`
> —— 本轮**没有**单独量 ⇒ **标【近似】，不是实测的平衡点**。

## §4 ★ 结论与建议（**这是要你拍板的地方**）

### 4.1 三条硬事实

1. **用户原话里的"用 CuPy 直接替换"如果按字面做（算子级替换），实测会让仿真变慢**
   （0.24–0.41×）。**这一条必须告诉用户**，不能默默照做。
2. **唯一可能有效的 GPU 路线是"状态常驻"**（整个 `advance` 搬 CuPy），
   实测上界 **1.49–1.58×**，但**收益完全由"每步往返几次"决定**，平衡点 **1.5 次/步**。
3. **CPU 线程那一半已经白赚 2.52×**（`R488_THREADSCALE.md`），**零风险、不动物理、
   且与 GPU 不冲突**（"多核 + GPU"可叠加）。

### 4.2 建议的顺序（**先做确定的那一半**）

```
第 1 步（已完成，立刻可用）：生产算例的 --nthreads 3 → 10~16   ⇒ **2.5×**
第 2 步（可选，需你定）：把 `advance()` 的**核心推进**整体搬到 CuPy（状态常驻）
        · 先做一个**小算例的 A/B 端到端对照**（同一算例、同一初态，只差后端）
        · **预登记判据**：整步墙钟加速 > 1.2× 才算成功
        · ⚠ 若实测 < 1，**按纪律如实报告并停手**，不要为了"用上 GPU"而硬搬
第 3 步：两者同时开（多核 + GPU）
```

### 4.3 ⚠ 我**没有**做的事（诚实交代）

* **没有**改引擎的 `--backend` 开关 —— 因为**第 2 步的可行性取决于端到端实测**，
  在拿到"整步 > 1.2×"之前写开关是**先做后验**（本仓库纪律：先框架、后代码）。
* **没有**声称"GPU 能加速仿真"。**实测支持的是**："算子级替换会变慢；
  常驻路线有小幅上界收益，但平衡点很紧"。

## §6 ⚠⚠ **勘误（2026-10-04）：B′ 是无效测量，§3 的分解作废**

### 6.1 指控

`_r490` 的 B′ 是这么写的：

```python
def mode_B():                    # ← B′ 就是它本身
    k  = cp.argmin(ph_g, axis=0)
    ef = e0_g[k.ravel()].T
    es = cp.einsum('vp,p...->v...', e0_g, sig_g)
    ff = cp.fft.fftn(ph_g[0]).real
    return k, ef, es, ff         # ← 返回 **CuPy 数组**，**从不 asnumpy / synchronize**

def mode_B_kernel_only():        # ← "上界参考"
    return mode_B()
```

**CuPy（与 CUDA 一致）是异步的**：`cp.argmin(...)` 只是**把核排进 CUDA 流就返回**。
不同步 ⇒ **CPU 根本不等待 GPU 算完** ⇒ 量到的是**提交耗时**，不是**计算耗时**。

### 6.2 实测（`_r558_gpu_bprime.py`，**先写死判据再跑**）

| 尺寸 | (a) 只提交（= B′） | (b) 提交 **+ `synchronize()`** | **(b)/(a)** | (c) 再加 `asnumpy` |
|---|---:|---:|---:|---:|
| abA (N=112, 0.26 GB, f64) | 0.000341 s | **0.020801 s** | **61.0×** | 0.193715 s |
| N=160 (1.95 GB, f32) | 0.000291 s | **0.024933 s** | **85.6×** | 0.975722 s |

* **S1/S2 ✅**：同步后慢 **61–86 倍**（判据 ≥5×）⇒ **B′ 确实没同步**。
* **S4 负对照 ✅**：4 元素数组上比值只有 **3.54×**（判据 <5）
  ⇒ 证明 S1 量的是**真计算**，不是固定开销。
* **⇒ B′（1200×/12344×）无效；§3 的「0.13% / 99.87%」分解无效。**

### 6.3 用**同步后的数**重算的正确分解（`S3`）

| 尺寸 | **GPU 计算** | **D2H 传输** | 提交 |
|---|---:|---:|---:|
| abA (0.26 GB) | **10.6%** | **89.3%** | 0.2% |
| N=160 (1.95 GB) | **2.5%** | **97.4%** | 0.0% |

⚠ **但这仍不是引擎每步的出行量**：本序列拷回的是 **`k` + `es` + `ff` 三个大数组**，
而真实引擎每步只需要 `region()`（一个 `N³` int16）。**⇒ 89–97% 这个比例
是**这个合成序列**的，不是引擎的。不得直接引用。**

### 6.4 哪些结论**不受影响**（重要）

**`A` / `B` / `CPU` 三行都调了 `cp.asnumpy(...)` ⇒ 都是同步过的有效测量**：

| 结论 | 是否受影响 |
|---|---|
| **算子级替换更慢**（A = 0.406× / 0.239×） | ✅ **不受影响**（有效） |
| **状态常驻只有 1.49–1.58×**（B） | ✅ **不受影响**（有效） |
| 数值一致 ✅、M4 负对照 ✅ | ✅ 不受影响 |
| **「B′ = 1200×/12344×」** | ❌ **作废** |
| **「0.13% 计算 / 99.87% 传输」** | ❌ **作废** |
| **「收支平衡点 = 1.5 次往返/步」** | ⚠ **降级为【近似】**（它是 `t_cpu/t_B` 的比值，成立；但作为"往返预算"需单独量 `t_transfer`，本轮没量） |

### 6.5 教训

> **计时一个异步 API 而不做同步 —— 这是 CuPy/CUDA 的经典陷阱**
> （`cupyx.profiler.benchmark` 存在的**唯一理由**就是替你做这件事）。
>
> **判据（以后一律照此）：凡计时 GPU 操作，必须① 显式 `synchronize()`
> 或② 用 `cupyx.profiler.benchmark`；并且③ 加一个"极小数组"负对照
> 确认量到的是真计算而非固定开销。**
> 本轮 `S4` 就是这个负对照，它**通过了** —— 也就是说**如果当初有这个负对照，
> 这个错当场就会被抓住**。

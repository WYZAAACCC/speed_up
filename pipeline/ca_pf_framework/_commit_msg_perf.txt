perf(R141): 消耗实测 —— 瓶颈 = advance（单线程 + 算力受限）；reinit 一次 = 16 步

新增脚本: _probe_cost.py / _probe_workers.py / _bench_adv.py / _run_bwtest.sh

一、24 µm 盒实测（多核 RVE n0=64，T16 口径）
  N=96  (Δx=250) 8.9e5 胞 : 峰值 1.52 GB, 3.32 s/步*（ed 0.44 + adv 2.90）
  N=192 (Δx=125) 7.1e6 胞 : 峰值 7.47 GB, 39.5 s/步 （ed 4.67 + adv 34.8）=> 15 µm 需 8.8 h
  N=384 (Δx=62.5) 5.7e7 胞: 构造期已 10.4 GB，仍在跑
  标度（胞数 ×8）: ed ×10.6, adv ×12.0, RSS ×4.9
  => 外推 N=384: ~470 s/步（8 min/步），1600 步 ≈ 8.7 天；RSS ≈37 GB > 22 GB => 大概率 OOM

二、reinit 是最大的单次开销（一次 = 16 个正常步）
  N=96 逐步: 3.20/3.36/3.28/3.44/3.20 s，第 6 步 53.89 s
  触发可预测并被两次独立验证:
    N=96  reinit_dt/dt = 6e-7/1.071e-7 = 5.60  => 第 6 步  OK
    N=192              = 6e-7/5.36e-8  = 11.2  => 第 12 步 => 1-6 步无尖峰 OK
  => 解释了"六步均值 11.75 vs cProfile 3.69"的 3 倍差

三、workers 只并行 FFT，主瓶颈完全单线程
  代码: windowB_pf3d.py:262,265 是唯一用 workers 的地方（scipy.fft）
  实测 N=128: advance 加速比 1.00/0.98/1.02/1.07/1.00（workers=1/4/8/16/20）
              advance CPU/wall 恒 1.03-1.15
              elastic_driving 加速比最高仅 ×1.27（workers=20）
  => 20 核机器上有效并行度约 1.1 核

四、advance 是算力受限，不是带宽受限 => 并行化值得做
  K 路并发聚合吞吐（N=96, 各 8 步）:
    K=1: 0.2847 steps/s
    K=2: 0.2260+0.2266 = 0.4526 steps/s => ×1.59 => 并行效率 0.79
  带宽佐证: 本机峰值带宽 8.15 GiB/s（triad 192 MB）；advance 每步 3.51 s
    => 带宽饱和需搬 ~30.7 GB/步，而全状态仅 92 MB => 需每步扫 330 遍，差两个数量级
  （K=2 的 21% 损失含 N=384 作业干扰 => 0.79 是下界）

五、优化杠杆排序（已由实测排序）
  1. 并行化 advance（占步时 88%，现 0 并行）—— 理论 4-8× 墙钟
  2. 降低 reinit 频率（从每 6 步到每 30 步 => 总时降 30-40%）—— 须做精度对照
  3. 调 workers —— 上限 ×1.27，收益小

⛔ 在 N=384 实测出来前，不得把"24 µm / 62.5 nm 跑得动"写成结论。

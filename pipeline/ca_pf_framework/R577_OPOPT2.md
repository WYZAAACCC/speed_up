## §1 `upwind_flux_vec` 重写：否定结果（goal §2）

### §1.1 先量后改（`_r577_ufv_bench.py`，N=64，交错配对 15 轮）

| 候选 | order=2 中位 | `max|Δ|/max` vs legacy | 结论 |
|---|---|---|---|
| `legacy`（生产现值） | 43.4 ms | 0（基准） | — |
| `rollip`（保留 `np.roll`，只把 `_minmod` 压成原地版 + 原地加） | 46.2 ms | **4.769e-02** ❌ | 更慢 **且** 不等价 |
| `slices`（切片移位替代 `np.roll` + 预分配缓冲 + `moveaxis`） | 43.4 ms | **4.769e-02** ❌ | 更慢 **且** 不等价 |
| `fused`（`np.where` 型 minmod，值等价） | 43.3 ms | 1.220e+00 ❌ | 参考用 |

配对比值（每轮 legacy/cand，15 轮）：`legacy/rollip` 中位 **0.887×**、`legacy/slices` 中位 **0.775×**
⇒ **两个候选都比 legacy 慢**（0.775× 意味着候选比 legacy 慢 29%）。

> ⚠ **`_r576` 的表把这一项排第一是有道理的**（`op.ufv.minmod` 占 31.1% 的单步），
> 但"占比大"**不等于**"有容易的提速"。**算子已经贴着 numpy 的逐元素成本跑了。**

### §1.2 为什么 `slices` 会"不等价"——抓到一个真实的语义细节

`windowB_surface.upwind_flux_vec` 的 order≥2 段：

```python
dm = dm + 0.5 * _minmod(dm - dmm, dp - dm)
dp = dp - 0.5 * _minmod(dpp - dp, dp - dm)      # ← 这里的 dm 是**上面刚更新的 dm**
```

第一行 **rebinding 了 `dm`** ⇒ 第二行里的 `dp - dm` 用的是 **`dp - dm_new`**，
**不是** `dp - dm_old`。

对比同文件的 `upwind_grad2`（第 68-69 行）：

```python
Dm2 = dm + 0.5 * _minmod(dm - dmm, dp - dm)
Dp2 = dp - 0.5 * _minmod(dpp - dp, dp - dm)     # ← 用的是 dm_old（因为 dm 没被改）
```

**两个函数在这一点上不一致**，而 `proj2`（生产默认的平流格式）走的是 `upwind_flux_vec`。
我把 `dp - dm` 提出来复用一次（一个很自然的"优化"）⇒ `max|Δ|/max = 4.769e-02`，
**是结构性差异，不是舍入**。

> ⇒ 这条**不是**要"修"的 bug（它已经是归档行为，改了就是改物理），
> 而是一条**必须记进文档的陷阱**：谁要动这个算子，必须知道这两处 `dp - dm` 取自不同的 `dm`。
> 逐位判据在这里**救了一次**：只比"快了多少"会把这个错当成一次成功的优化。

### §1.3 还试过但**没进候选表**的两条（也记账）

* **§1.3a** `dp = np.roll(dm, -1, axis=ax)` —— 数学上 `D⁺φ[i] = D⁻φ[i+1]`，**逐位相同**，
  可省 1 次减法 + 1 次除法。实测收益在噪声内（`op.ufv.diff` 一共只占 6.5%）⇒ **未采纳**（不做无用改动）。
* **§1.3b** 用 `math`/`numexpr` 融合表达式 —— numpy 无融合，本项目无 `numexpr` 依赖 ⇒ **不引入新依赖**。

## §2 ★★★ 分配器环境变量：1.78× 的墙钟，只换 19% 的峰值 RSS

### §2.1 怎么发现的

`_r576` 的账把"临时量"顶到了台面上：`upwind_flux_vec` 一次调用要造 **~35 个整场临时量**
（N=64 每个 2 MB）⇒ 单步 ~0.9 GB 的 malloc/free。
而 glibc 默认 `M_MMAP_THRESHOLD = 128 KB` ⇒ 这些 2 MB 的块**全部走 mmap**。
顺着这条线去查环境，发现**本仓库 `ca_pf_framework/` 下 523 个 `.sh` 里有 124 个**写着：

```bash
export MALLOC_MMAP_THRESHOLD_=65536 MALLOC_TRIM_THRESHOLD_=65536 MALLOC_ARENA_MAX=2
```

`_bk_run_block.sh:10` 的注释说明了它当年为什么被加进来：
> 「解法：`MALLOC_MMAP_THRESHOLD_` 调小 ⇒ 大块走 mmap ⇒ free 时**真的归还**」

—— 这是**为了控内存**，不是为速度。而它到底让速度掉了多少，**从来没人量过**。

### §2.2 实测（`_r577_env_ab.sh`，交错 3 轮）

| | 单步（3 轮） | 配对提速 |
|---|---|---|
| PLAIN（不设任何 MALLOC 变量） | 0.4461 / 0.4381 / 0.4091 | — |
| TUNED（三个全开） | 0.7858 / 0.7168 / 0.7282 | **0.568×**（= 慢 1.76×） |

内部读数一致：`adv.step.advphi`（分配最密的算子）PLAIN 0.2119/0.2024/0.1967 →
TUNED 0.5127/0.5323/0.5222 ⇒ **0.380×**（慢 2.63×）。

### §2.3 逐项拆开（`_r577_alloc_ab.sh`，五臂交错 3 轮 + `/usr/bin/time -v`）

| 臂 | 单步（3 轮） | 相对 PLAIN 中位 | 峰值 RSS |
|---|---|---|---|
| **PLAIN** | 0.4160 / 0.4224 / 0.3282 | **1.00×** | **520 MB** |
| `MALLOC_MMAP_THRESHOLD_=65536` | 0.7156 / 0.7007 / 0.5007 | **1.66×** | 418 MB |
| `MALLOC_TRIM_THRESHOLD_=65536` | 0.7308 / 0.7053 / 0.7296 | **1.76×** | 418 MB |
| `MALLOC_ARENA_MAX=2` | 0.3884 / 0.3890 / 0.4294 | **0.93×**（更快） | 472 MB |
| 三个全开（= 仓库脚本的写法） | 0.7394 / 0.6993 / 0.7308 | **1.78×** | 416 MB |

**读法**：
* **元凶是 `MMAP_THRESHOLD` / `TRIM_THRESHOLD`**（两者单独都足以造成 ~1.7×）。
  它们的收益是峰值 RSS **520 → 418 MB（−19%）**。
* **`MALLOC_ARENA_MAX=2` 是"免费的好事"**：墙钟 0.93×（略快），峰值 RSS 从 520 → **472 MB**（也降）。
  【推理】限制 arena 数减少了 4 个工作线程之间的 slab 碎片 ⇒ 既省内存又不撞 malloc 锁。

### §2.4 ★ 真实路径验证（`_r577_realalloc.sh`，`_bk_exp.py` 30 步 / N=64 / 2 线程）

| 轮 | PLAIN s/步 | TUNED s/步 | 配对提速 | PLAIN 峰值RSS | TUNED 峰值RSS |
|---|---|---|---|---|---|
| 1 | 0.4050 | 0.6900 | 0.587× | 428 MB | 384 MB |
| 2 | 0.4450 | 0.7000 | 0.636× | 423 MB | 384 MB |

* **中位 0.61×（TUNED 慢 1.64×）** —— 与引擎单步的 1.78× 同量级 ⇒ **效应在真实路径上成立**。
* **`series.csv` 共有列（96 列）逐位一致，最大相对差 = 0.000e+00** ⇒ 分配器**不参与数值**
  （所以换它不需要重跑任何物理判据，只需要过回归）。
* RSS 只从 428 → 384 MB（**−10%**）⇒ 这个代价更不划算。

> ⚠ **口径记账**：`_r569_smoke.sh`（真实路径冒烟）**本身就设了那三个变量**
> ⇒ **R561–R576 的所有"真实路径"数字都是在慢路上量的**（OFF 0.465 / BIT 0.435 / ON 0.410）。
> 这不影响那些**比值**（两臂同环境），但影响所有**绝对秒数**。

### §2.5 ⚠ 三条必须先补的证据（不许直接照搬结论 / 不许现在改脚本）

1. **RSS 只看了峰值，没看"长跑是否单调增长"**。mmap/trim 阈值当年是为**归还内存**加的，
   担心的场景是"长跑 RSS 越滚越大 ⇒ WSL 24 GB 撞 swap"。
   **峰值降 10% 不等于长跑不涨** ⇒ 必须做**长跑 RSS 轨迹**（每 N 步记一次 RSS）才能判。
   （`_r30_regress.sh` 的 200 步 N=96 正好可以当载体。）
2. **N=64/nv=24 与真实生产（N=160/nv≈359）的临时量规模不同**，缺页/TLB 代价不同
   ⇒ 必须在 **N=160** 上复测一次。
3. **不许直接改那 124 个脚本**。正确做法是加一个**显式档位**
   （如 `WB_ALLOC=plain|tuned|arena`，默认 `tuned` = 现状），并在每个基准脚本里
   **打印它实际用的是哪一档**（否则又会造出"两次测量环境不同却看不出来"的坑）。

**⇒ 本项作为新条目登记：`--alloc {default,arena,legacy}` 三档开关 + 长跑 RSS 轨迹 + N=160 复测。
在拿到那三项证据之前，不许改任何生产脚本的环境变量。**

## §4 本轮新增的纪律

1. **"占比大"不是"能提速"**：`op.ufv.minmod` 占 31.1%，但三个重写全更慢。
   ⇒ 动大算子前**先做候选微基准**，不要直接改生产代码。
2. **逐位判据不只是防舍入**：它在 §1.2 抓到的是一个**语义提取错误**（`dp - dm` 取自哪个 `dm`）。
   ⇒ 凡"提取公因式"的重写，**必须**过逐位判据。
3. **环境变量也是代码**：本仓库 124 个脚本（共 523 个）带着同一行 `export MALLOC_*`，
   从来没人量过它的性能代价 —— **实测 1.78×**。
   ⇒ 基准脚本必须**显式记录**它有没有设这些变量（否则跑出来的数不可比）。
4. **跨会话绝对值不可比**（R576 §8）：同一份代码同一命令的单步墙钟在不同会话里差 1.5×，
   而逐步回归的 `s/步` 一字不差 ⇒ **只信交错配对的比值**。
